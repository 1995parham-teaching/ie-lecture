MVC: Model-View-Controller

  • Model
    • Does all the computational work
      • It contains data and performs computation on it
  • View (the user interface)
    • Shows the results from the model or the controller
  • Controller (of state sequences)
    • Handles events/requests affecting model or view
      • User inputs/requests go to the controller
      • Available commands are determined by controller (based on model)
      • Tells the model what to do
  • Examples
    • MS Excel
    • Your lecture 7 Go server: the handler is the C, the Student struct is the M, and the JSON encoding is the V

MVVM Design Pattern

  • What is the role of the controller in MVC?
    • Basically updates V by changes in M and vice versa
  • Instead of coding the C, make it automated
    • Automatically update M by changes in V
    • Automatically update V by changes in M
    • Two-way binding
  • The Model-View-ViewModel pattern
    • The view model is a value converter
    • Responsible for exposing (converting) the data objects from the model in such a way that objects are easily managed and presented.

Design Pattern in Modern Apps

  • Apply the design pattern in client side and server side separately
  • Client side frameworks

    • Django, Rails, Laravel: MVC (Django calls the controller a "view")
    • Spring: MVC

Layering Approach

  • Common layering in web applications
    • Presentation Layer
    • Business logic Layer
    • Data (management/resource) Layer
  • These layers are purely abstractions
    • They do not correspond to physical distribution
      • All layers may or may not be on the same machine
    • Physical layering is referred to as multi-tier architecture

Multilayer Architecture

Your Lecture 7 Server, Layered

The same net/http server as go-lecture/httpserver, now with students. The handler never sees SQL; the data layer is an interface.

Data Layer: an Interface

type Student struct {
  ID        int64  `json:"id"`
  FirstName string `json:"first_name"`
  LastName  string `json:"last_name"`
}

// data layer: the layers above see only this interface
type StudentStore interface {
  Get(id int64) (Student, error)
}

var ErrNotFound = errors.New("student not found")

// MemStore is one implementation; a PostgresStore would be another
type MemStore map[int64]Student

func (m MemStore) Get(id int64) (Student, error) {
  s, ok := m[id]
  if !ok {
    return Student{}, ErrNotFound
  }
  return s, nil
}

Business Layer, and the Wiring

// business layer: the rules, written against the interface
type StudentService struct{ Store StudentStore }

var ErrBadID = errors.New("student id must be positive")

func (s StudentService) Find(id int64) (Student, error) {
  if id <= 0 {
    return Student{}, ErrBadID
  }
  return s.Store.Get(id)
}

func main() {
  store := MemStore{
    9531: {ID: 9531, FirstName: "Linus", LastName: "Torvalds"},
  }
  h := StudentHandler{Svc: StudentService{Store: store}}

  mux := http.NewServeMux()
  mux.HandleFunc("GET /students/{id}", h.Get)
  log.Fatal(http.ListenAndServe("127.0.0.1:1373", mux))
}

Presentation Layer: the Handler

// presentation layer: HTTP in, JSON out; no SQL, no rules
type StudentHandler struct{ Svc StudentService }

func (h StudentHandler) Get(w http.ResponseWriter, r *http.Request) {
  id, err := strconv.ParseInt(r.PathValue("id"), 10, 64)
  if err != nil {
    http.Error(w, "bad id", http.StatusBadRequest)
    return
  }
  s, err := h.Svc.Find(id)
  switch {
  case errors.Is(err, ErrNotFound):
    http.Error(w, err.Error(), http.StatusNotFound)
    return
  case err != nil:
    http.Error(w, err.Error(), http.StatusBadRequest)
    return
  }
  w.Header().Set("Content-Type", "application/json")
  _ = json.NewEncoder(w).Encode(s)
}

Service-oriented architecture (SOA)

  • The SOA-based approach helped IT professionals build applications (services) with well-defined interfaces that abstract the internal implementation details so that the consumers of these applications would only need to integrate through the interface.
  • The SOA-based approach allowed application developers to change their internal implementations more freely, as long as they adhered to the interface definitions.

Scaling: Monolith vs. Microservices

The Four Tiers of a Microservice Application

What Makes Microservices Challenging?

  • Scoping and identifying microservices requires substantial domain knowledge.
  • The right boundaries and contracts between services are difficult to identify and, once you've established them, can be time-consuming to change.
  • Microservices are distributed systems and therefore require different assumptions to be made about state, consistency, and network reliability.
  • By distributing system components across networks, and increasing technical heterogeneity, microservices introduce new modes of failure.
  • It's more challenging to understand and verify what should happen in normal operation.

When Not to Use Microservices

  • Monolith First (Fowler, 2015):
    • "Almost all the successful microservice stories have started with a monolith that got too big and was broken up."
    • Systems built as microservices from scratch mostly ended up in serious trouble.
  • Small team, new product, boundaries not clear yet: start with a well-layered monolith
  • Split out a service when one part must scale, fail or deploy on its own

Atomicity

  • Transactions are often composed of multiple statements
  • Atomicity guarantees that each transaction is treated as a single "unit", which either succeeds completely, or fails completely
    • if any of the statements constituting a transaction fails to complete, the entire transaction fails and the system is left unchanged.

Fixing It: Outbox and Idempotent Consumers

CAP Theorem

During a network partition, a distributed data store must choose between consistency and availability:

  • Consistency: Every read receives the most recent write or an error
  • Availability: Every request receives a (non-error) response, without the guarantee that it contains the most recent write
  • Partition: an arbitrary number of messages between nodes are dropped (or delayed) by the network. Networks do partition, so this is not optional.

"Pick 2 of 3" is the popular form; Brewer (2012) calls it misleading. With no partition, a system can be both.

CAP During a Partition

MongoDB (CP)

  • A replica set has exactly one primary, which takes every write; the secondaries replicate it.
  • Data is stored as BSON documents (binary JSON) in the WiredTiger storage engine.
  • If the primary node becomes inaccessible, then one of the secondary nodes needs to become the primary node.
    • Until a new primary is elected from amongst the secondary nodes, the system remains unavailable to the user to make any new write query.
    • Therefore, the MongoDB system behaves as a Consistent system and compromises on Availability during a partition.
  • CP only with write concern majority (the default since 5.0) and reads from the primary; a read from a secondary may be stale.

Cassandra (AP)

  • Cassandra is a peer-to-peer system of many nodes, and each node can accept a read or write request from the user.
  • Cassandra maintains multiple replicas of data in separate nodes
  • During a partition a replica may not get the update: it stays available, but its data is inconsistent.
  • All updates reach all the replicas eventually; meanwhile, divergent versions of the same data can exist.
  • Consistency is tunable per query: with 3 replicas, QUORUM (2 of 3) writes and reads overlap, so a read sees the latest write.

Messaging patterns used in distributed systems

  • Remote procedure calls (RPC) versus shared resources
  • Synchronous versus asynchronous (client-server versus pub-sub)
  • Orchestration versus choreography

Remote procedure calls (RPC) versus shared resources

Between microservices a shared database is an anti-pattern: each service owns its data (database per service) and others reach it only through its API.

Synchronous versus asynchronous

Client-server is synchronous; publish-subscribe through a message broker is asynchronous.

Orchestration versus choreography

Choreography is borrowed from dance: the steps are designed in advance, and nobody conducts during the show.

Asynchronous Messages

By announcing events, services no longer need to know their downstream consumers, so the system is easy to extend. The broker routes each event by its subject.

Quality of Service

Guarantee MQTT Lost? Duplicated?
at-most-once (fire and forget) QoS 0 maybe never
at-least-once QoS 1 never maybe
exactly-once QoS 2 never never
  • At-least-once means the consumer must be idempotent: handling a message twice has the same effect as once.
  • MQTT's exactly-once holds per hop (client ↔ broker), not end to end.

REST

  • REpresentational State Transfer: an architectural style (Fielding, 2000), not a protocol
  • Resources are named by URLs: /students/9531
  • The standard HTTP methods act on them: GET reads, POST creates, PUT replaces, DELETE removes
  • The server sends a representation of the resource, usually JSON
  • Stateless: each request carries everything the server needs
  • Example: GET /students/9531 → 200 and the student as JSON (the layered server)

North-South vs. East-West

North-South traffic

In a typical enterprise platform, North-South traffic is the more sensitive and customer-facing communication flow that attracts the maximum attention from everyone.

  • REST
  • GraphQL
  • WebSocket

East-West traffic

Most of the time, architects and technical leads give priority to the consumer-facing interfaces and they let developers decide on the internal communication between services.

  • HTTP (REST)
  • NATS
  • Kafka
  • gRPC
